# Implementation Plan: Ticket Triage Dashboard

**Branch**: `001-ticket-triage-dashboard` | **Date**: 2026-09-06 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-ticket-triage-dashboard/spec.md`

## Summary

Give the PMO coordinator one screen that replaces a three-source manual
reconciliation: every open ticket, grouped into P0/P1/P2 sections with a count
badge on each, plus the ability to retag a ticket's priority and owner and have
that decision stick.

Technical approach: a single Next.js 15 App Router project where the dashboard is
a server component reading through Prisma directly (no client fetch waterfall, so
the 1.5s render budget is met by construction), and the same data is exposed as
route handlers (`GET /api/tickets`, `PATCH /api/tickets/:id`) that form the one
contract the UI also writes through. Zod validates at two boundaries — the seed
loader and the PATCH handler — so an invalid priority or unknown owner can never
reach the database. Both editable fields are closed-choice controls, making the UI
structurally incapable of submitting the states the API is nonetheless required to
reject.

## Technical Context

**Language/Version**: TypeScript 5.x, `strict: true`, on Node.js 20 LTS

**Primary Dependencies**: Next.js 15 (App Router, React 19), Prisma 6 (client +
migrate), Zod 4. Dev only: Vitest, ESLint (`next lint`), `tsx` for the seed script.

**Storage**: SQLite via Prisma, single local file (`prisma/dev.db`), gitignored and
regenerated by migration + seed. Two tables: `Ticket` and `Owner`.

**Testing**: Vitest for unit, contract, and integration tests. Route handlers are
invoked directly as functions against a temporary SQLite file — no HTTP server and
no browser driver, which is what keeps the whole pipeline inside the 3-minute
budget. The CI "smoke test" is an integration test asserting the dashboard page
renders its three groups with correct counts from a known seed.

**Target Platform**: Desktop browser (current Chrome/Edge/Firefox) against a
locally run Next.js server. No deployment target in scope.

**Project Type**: Web application — single Next.js project serving both UI and API
from one build, per ADR-001.

**Performance Goals**: Initial dashboard render < 1.5s on localhost with the seed
set (NFR-1). `GET /api/tickets` and `PATCH /api/tickets/:id` p95 < 150ms (NFR-2).
Full CI pipeline < 3 minutes (NFR-3).

**Constraints**: Zero `any` types, `tsc --noEmit` clean (NFR-4). 100% of write
payloads Zod-validated before any state change (NFR-5). Exactly one structured log
line per API request, with a failure reason on 4xx/5xx (NFR-7). Signed
Conventional Commits (NFR-6). No authentication, no ingestion, no create/delete, no
notifications, no analytics (NG-1..NG-5).

**Scale/Scope**: ~40–60 open tickets, a handful of owners, one concurrent user.
Roughly 3 UI components, 2 route handlers, 1 seed script, 1 CI workflow. No
pagination, search, or virtualisation at this size (A-006).

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Gate | Initial | Post-Design |
|---|---|---|---|
| I. Type Safety Is Non-Negotiable | `strict: true`; zero `any`; all data access via Prisma typed client; ticket shape defined once and derived everywhere | PASS | PASS |
| II. Validate At The Boundary | Zod schema at every write boundary, before any state change; priority constrained to P0/P1/P2; no duplicated validation inside handlers or persistence | PASS | PASS |
| III. Scope Discipline (YAGNI) | Nothing outside G-1..G-5; all five Non-Goals respected | PASS *(with one justified addition — see Complexity Tracking)* | PASS |
| IV. Diagnosable By Default | Exactly one structured log line per API request: method, path, status, duration; plus failure reason on 4xx/5xx | PASS | PASS |
| V. Green Pipeline Or Not Done | CI runs lint, type check, test, build; Prisma migration runs clean in CI; signed Conventional Commits | PASS | PASS |

**Initial evaluation notes:**

- **Principle I** is the reason the UI calls the same route handlers the API
  exposes rather than duplicating query logic: one `Ticket` type flows from
  `schema.prisma` through the Prisma client into both halves, so the shape cannot
  drift (the specific failure ADR-001 names).
- **Principle II** has two boundaries in this design, not one: the PATCH handler
  (FR-008) and the seed loader (FR-012). Both use schemas exported from a single
  module so the priority and owner rules are stated exactly once.
- **Principle III** is the tightest gate here. The design adds an `Owner` table,
  which is a second entity where ADR-002 named only `Ticket`. It is required by
  FR-015 and justified in Complexity Tracking below rather than waved through.
- **Principle IV** drove the choice of a route-handler wrapper over Next.js
  `middleware.ts`; see research.md R2 for why middleware cannot satisfy NFR-7.

**Post-design re-evaluation:** No new violations. The Phase 1 design added no
entities, endpoints, or dependencies beyond those evaluated above. The one item in
Complexity Tracking is unchanged in scope and remains justified.

**Structure Decision**: Single Next.js project, not a backend/frontend split.
ADR-001 accepted one framework serving both halves specifically to avoid two
builds, two run commands, and CORS between them. The API lives at
`src/app/api/tickets/` as colocated route handlers, the UI at `src/app/page.tsx`,
and everything they share — schemas, grouping rules, logging, database access —
lives in `src/lib/` so neither half owns logic the other needs. Business logic is
kept out of components and route handlers so it is unit-testable without rendering
or HTTP.

## Complexity Tracking

> **Fill ONLY if Constitution Check has violations that must be justified**

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| A second entity (`Owner` table) where ADR-002 specifies only `Ticket` | FR-015 requires the known owner list to be declared in the seed file and read-only, and FR-008 requires every update to check owner membership. A table makes that check a foreign key the database enforces, so an invalid owner cannot be written even if application validation is bypassed — which is what Principle II asks for. | *Storing owners as a JSON array in a config module* was rejected because membership then rests entirely on application code, with no database-level guarantee, and the owner list could drift from the owners actually referenced by tickets. *Deriving the list from distinct `Ticket.owner` values* was rejected during clarification (Q4): it makes a newly onboarded person unassignable until they already own a ticket. |

**Not counted as violations:**

- **Two Zod boundaries instead of one.** FR-008 and FR-012 are genuinely two entry
  points for untrusted data (an HTTP payload and a file on disk). Both import the
  same schemas from `src/lib/schemas.ts`, so the rule is written once — this
  satisfies Principle II rather than straining it.
- **`priority` stored as `String` rather than a database enum.** Not a design
  preference: Prisma does not support enums on the SQLite provider (research.md
  R6). The three-value constraint is enforced by Zod at both write boundaries and
  by a TypeScript union used throughout, so no `any` and no invalid value reaches
  the data layer.
